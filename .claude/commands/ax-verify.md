`$1` 이슈 `$2`를 검증한다. `stage`가 `built`여야 한다.

`spec.md`의 수용기준 표가 이 단계의 입력이다. AC ID 하나하나에 판정을 낸다.

## 6-A 기계 검증

빌드 · 테스트 · 린트를 돌린다. 실패하면 여기서 멈추고 5번으로 돌려보낸다.

## 6-B spec 대조 — 헤드리스

**코드를 쓴 컨텍스트가 자기 작업을 채점하면 안 된다.** 별도 프로세스를 띄운다.

```
claude -p "<spec.md 경로>의 수용기준 표를 읽고, 아래 diff가 각 AC를 충족하는지 항목별로 판정하라.
PASS / FAIL / UNVERIFIABLE 중 하나와 근거가 될 파일·라인을 대라.
충족한다고 단정하지 말고 반증을 먼저 시도하라." --output-format json
```

diff는 기본 브랜치 대비 전체를 넘긴다. 판정 결과를 그대로 받아 적는다 — 마음에 안 든다고 고쳐 쓰지 않는다.

## 6-C 화면 검증 — FE 이슈만

Chrome 확장으로 앱을 직접 조작한다.

1. 레지스트리 `app.start`로 앱을 띄우고 `app.url`로 접속한다. 값이 비어 있으면 사람에게 물어 채운 뒤 `projects.yml`에 기록한다
2. 수용기준의 시나리오를 순서대로 실제로 조작한다. 코드를 읽고 "될 것 같다"고 판정하지 않는다
3. **확인 지점마다 스크린샷을 `<spec_dir>/items/<번호>/docs/shots/`에 저장한다.** 파일명은 `ac-1-<설명>.png`
4. 이 캡처가 7번 문서의 자료가 된다. `spec.md`의 문서 반영 포인트 목록을 함께 훑어 빠진 화면이 없게 한다

**짝 BE가 미머지면** 화면이 동작하지 않는다. 짝 브랜치를 함께 체크아웃해 통합 상태로 검증한다. 그게 안 되면 6-C를 `보류`로 남기고 6-A·6-B만 판정한다 — 통과로 처리하지 않는다.

## 6-D API 계약 검증 — BE 이슈, 그리고 화면 없는 항목

실제 요청을 쏘고 응답을 `spec.md`의 스키마와 대조한다. 정상 경로만이 아니라 빈 값·오류·경계값도 친다.

## 판정

`templates/verify.md`로 `verify.md`를 쓴다. AC ID별 판정과 근거, 캡처 경로를 남긴다.

- `FAIL`이 하나라도 있으면 → 5번으로 되돌린다. `stage`는 올리지 않는다
- `UNVERIFIABLE`은 사람에게 판단을 넘긴다
- 전부 `PASS`면 `gates.verify`에 시각을 적고 `stage`를 `verified`로 올린다

**통과시키고 싶어서 판정을 무르게 하지 않는다.** 여기서 놓친 것은 문서에 그대로 실려 현업에 나간다.
