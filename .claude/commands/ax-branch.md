`$1` 프로젝트의 이슈 `$2`에 대한 브랜치를 만든다.

## 1. 상태 확인

`.ax/state/$1/` 에서 해당 이슈 상태를 읽는다. `stage`가 `synced` 이상이어야 한다. 아니면 `/ax-sync $1` 부터 하도록 안내한다.

## 2. 워크스페이스 준비

레지스트리의 `workspace` 경로에 클론이 없으면 먼저 클론한다.

```
gh repo clone <slug> <workspace>
```

있으면 기본 브랜치로 이동해 최신화한다.

## 3. 의존 점검

`depends`에 걸린 이슈 중 아직 머지되지 않은 게 있으면 **경고를 띄우고 계속할지 묻는다.** 특히 FE 이슈인데 짝 BE가 미머지면 6-C 화면 검증을 단독으로 통과할 수 없다는 점을 알린다.

## 4. 기존 관례부터 본다

**브랜치를 만들기 전에 `git branch -r` 로 원격을 훑는다.**

이미 이 작업과 관련된 브랜치가 있으면 새로 만들지 않는다. 파이프라인이 자기 규칙을 들고 들어가면 기존 작업과 갈라져서 둘 다 반쪽이 된다.

- 같은 이슈의 브랜치가 이미 있다 → 그걸 체크아웃한다
- 리포에 다른 명명 관례가 보인다 → 레지스트리 `branch_pattern`이 그 관례와 다르면 **멈추고 알린다.** 임의로 고르지 않는다
- 브랜치들이 서로 쌓여 있는 구조(stacked)라면 base가 기본 브랜치가 아닐 수 있다. 어디서 따야 하는지 확인한다

## 5. 브랜치 생성

레지스트리의 `branch_pattern`을 쓴다. 치환 가능: `{kind}` `{number}` `{slug}` `{item}`
기본값은 `feat/{kind}/{number}-{slug}`.

`slug`는 제목에서 개발항목 대괄호를 뗀 뒤 소문자 영숫자와 하이픈으로 만든다. 한글 제목이면 짧은 영문 요약을 직접 짓는다.

`base`는 레지스트리 값을 쓴다. **`main`이라고 가정하지 않는다** — `master`인 리포가 흔하다.

## 6. 기록

상태 파일에 `branch`를 적고 `stage`를 `branched`로 올린다.
